## 7) Regras para Samba (SMB) – detalhes
Samba usa TCP 445, TCP/UDP 139, UDP 137-138. Firewalld serviço "samba" cobre isso; se usar Samba personalizado, abra portas explicitamente:

```bash
sudo firewall-cmd --permanent --zone=home --add-port=445/tcp
sudo firewall-cmd --permanent --zone=home --add-port=139/tcp
sudo firewall-cmd --permanent --zone=home --add-port=137-138/udp
sudo firewall-cmd --reload
```

Se quiser restringir Samba a IPs da LAN (mais seguro):

```bash
sudo firewall-cmd --permanent --zone=home --add-rich-rule='rule family="ipv4" source address="192.168.1.0/24" service name="samba" accept'
sudo firewall-cmd --permanent --zone=home --add-rich-rule='rule family="ipv4" source address="0.0.0.0/0" service name="samba" reject'
sudo firewall-cmd --reload
```

Altere a rede conforme sua subnet.

## 8) Bloquear tudo por padrão (opção mais rígida)
Para comportamento "bloquear tudo exceto", crie zona customizada "locked" com target DROP e só permitir entradas de serviços através de rich rules.

Exemplo:

```bash
sudo firewall-cmd --permanent --new-zone=locked
sudo firewall-cmd --permanent --zone=locked --set-target=DROP
sudo firewall-cmd --permanent --zone=locked --add-interface=enp3s0
# permitir SSH apenas de LAN:
sudo firewall-cmd --permanent --zone=locked --add-rich-rule='rule family="ipv4" source address="192.168.1.0/24" service name="ssh" accept'
# permitir samba e https da LAN
sudo firewall-cmd --permanent --zone=locked --add-rich-rule='rule family="ipv4" source address="192.168.1.0/24" service name="samba" accept'
sudo firewall-cmd --permanent --zone=locked --add-rich-rule='rule family="ipv4" source address="192.168.1.0/24" service name="https" accept'
sudo firewall-cmd --reload
```

Isso descarta todo o tráfego não explicitamente aceito.

**Depois:** superfície reduzida — só SSH, Samba e HTTPS permitidos (e só da LAN se configurado), tráfego não autorizado é descartado/logado.

## Principais vetores de risco antes → depois

- Porta aberta/serviço exposto
  - Antes: serviços extras (ex.: RDP, SMB sem restrição, impressoras, mDNS) podiam aceitar conexões de qualquer host na LAN ou da internet se NAT/porta no roteador estava ativo.  
  - Depois: apenas portas necessárias (22, 445/139/137-138 UDP, 443) aceitas; outras portas bloqueadas pelo host. Resultado: menos vetores para exploração.

- Acesso remoto externo
  - Antes: se roteador tinha forwarded ports, atacantes na internet podiam tentar brute-force/exploits em serviços; mesmo sem NAT, dispositivos na mesma rede podiam escanear e explorar hosts.  
  - Depois: se você restringiu origem a 192.168.1.0/24 e não expôs portas no roteador, tentativas externas falham; ataques dentro da LAN ainda possíveis, mas limitados ao serviços abertos.

- Movimento lateral (lateral movement)
  - Antes: hosts com serviços amplos permitiam que um dispositivo comprometido alcançasse outros via SMB/RPC/SSH sem barreiras.  
  - Depois: zone locked e regras por origem limitam comunicações; movimento lateral exige que atacante esteja na LAN e consiga usar serviços permitidos ou comprometer credenciais.

- Exploração de vulnerabilidades em serviços
  - Antes: serviços desnecessários aumentavam chance de haver um serviço vulnerável.  
  - Depois: reduzir serviços diminui probabilidade de encontrar uma vulnerabilidade explorável.

- Exfiltração de dados
  - Antes: conexões de saída possivelmente livres; malware podia empurrar dados para destinos externos.  
  - Depois: firewalld padrão por host controla portas de entrada; por padrão não bloqueia totalmente saída a menos que você configure, então exfiltração por saída TCP 443 ainda possível — se quiser bloquear saídas, adicione regras de egress.

---

## Probabilidades (qualitativas)
- Chance de ataque remoto via internet: **Antes — moderada/alta** (se havia port forwarding); **Depois — baixa** (se não expôs portas no roteador + host bloqueado).  
- Chance de ataque por usuário malicioso dentro da LAN: **Antes — moderada**; **Depois — reduzida, mas não zero** (depende de serviços permitidos e senhas).  
- Chance de roubo de dados por malware com saída padrão (HTTPS): **Antes — alta**; **Depois — ainda possível** (firewalld por padrão não bloqueia saída; bloquear egress reduz muito essa chance).  
- Chance de movimento lateral a partir de um host comprometido: **Antes — alta**; **Depois — significativamente menor** (regras restrictivas e origem limitada).

---

## Formas de ataque práticas — antes vs agora

- Escaneamento de portas
  - Antes: nmap identificava muitas portas abertas; atacante podia explorar.  
  - Agora: nmap verá apenas 22, 445, 443 (ou menos se restrito por IP).

- Brute-force SSH
  - Antes: conexões SSH aceitas de qualquer IP na LAN/Internet; força bruta mais fácil.  
  - Agora: se SSH limitado à LAN e com fail2ban/key auth, brute-force externo bloqueado; interno ainda possível.

- Exploração SMB (roubo via shares / EternalBlue-like)
  - Antes: SMB exposto facilitava exploração e roubo de arquivos.  
  - Agora: SMB restrito à LAN/subnet — reduz risco; se combinado com contas fortes e atualizações, risco fica baixo.

- Exfiltração via HTTPS
  - Antes: malware podia trafegar por 443 sem restrição.  
  - Agora: ainda possível a não ser que implemente bloqueio de saída ou inspeção TLS (mais complexa).

---

## Recomendação rápida para reduzir ainda mais risco (prioridade)
1. Habilitar autenticação por chave para SSH e usar fail2ban.  
2. Restringir Samba a sub-rede específica e usar permissões de arquivo/contas fortes.  
3. Considerar bloquear tráfego de saída indesejado (egress) ou criar whitelist de destinos críticos.  
4. Manter sistema e Samba/serviços atualizados.  
5. Habilitar logs e revisar tentativas bloqueadas regularmente.  
6. Backup cifrado dos dados críticos.
